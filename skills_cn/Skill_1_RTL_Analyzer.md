# RTL 分析

生成 Testbench 前必须执行本阶段。

```text
本阶段出口条件：
用户已确认设计目标。
用户已确认测试目标。
若无需求文档，已生成维护文档。
```

## 步骤

### 1. 搜索需求文档

搜索工作区中文档，优先关注文件名或内容包含：

`需求`、`规格`、`设计说明`、`设计目标`、`测试用例`、`验证目标`、`requirement`、`spec`、`design`、`README`、`test case`、`verification`。

若找到文档，只读取和以下内容相关的部分：

- 设计目标
- 接口行为
- 时序或延迟约束
- 边界条件
- 测试用例或验证目标

### 2. 分析 RTL

阅读 `.v`、`.sv` 文件，报告：

- Top Module 候选
- 子模块层级
- 时钟和复位
- 关键输入输出
- 状态机、计数器、握手和数据通路

若有需求文档，必须比对：

- 与目标一致的功能
- 不明确的假设
- 疑似不一致点
- 需要用户确认的问题

若无需求文档，根据 RTL 推断设计目标，并标注为推断。

### 3. 确认设计目标

**停下来询问用户：**层级结构、设计目标、关键监控信号是否正确。用户确认或修正前，不进入测试规划。

### 4. 确认测试用例

设计目标确认后：

- 若文档有测试用例，按类别汇总。
- 若文档没有测试用例，主动提出建议：复位、基础功能、边界输入、连续/突发输入、非法/协议场景、延迟、关键状态跳转。

**停下来询问用户是否补充、删减或调整测试用例。**

### 5. 生成维护文档

仅当未找到需求文档时执行。用户确认设计目标和测试用例后，创建项目维护文档，建议路径：

```text
./rtl_verify_requirements.md
```

文档至少记录：

- 设计目标
- Top Module 和接口假设
- 关键时序/协议行为
- 用户确认过的测试目标
- 测试用例列表
- 未确认或后续待补充事项

### 6. 制定 Testbench 方案

用户确认测试目标后，再选择：

1. 生成新的自检 Testbench。
2. 在现有 Testbench 中注入 monitor 和 assertion。

必须使用结构化日志：

```verilog
$display("[TB_MONITOR] Time: %0t | State Changed: %0d -> %0d", $time, old_state, new_state);
$display("[TB_DATA] Time: %0t | Data = 0x%h", $time, data_out);
$error("[TB_ERROR] Time: %0t | reason", $time);
$display("[TB_INFO] Simulation Finished!");
```

协议和数据正确性使用 SVA 或行为级检查。
